# MODULE‑8  
# User Space ↔ Kernel Space Interaction  
*How Applications Control Hardware in Embedded Linux*

---

## Purpose: This module explains **how user‑space applications legally and safely interact with the Linux kernel** to control hardware.

By the end of this module, you will be able to:

- Understand **how user programs cross into kernel space**
- Clearly explain **system calls and kernel mediation**
- Understand **/dev, /sys, /proc as kernel interfaces**
- Distinguish **sysfs vs device‑file based access**
- Understand **where character drivers fit**
- Be fully prepared for **Module‑9: Character Device Driver**

This module is the **bridge** between:

- Applications (Phase‑1)  
- Drivers (Module‑9)

---

## TOPIC‑1: The Fundamental Rule

- User space cannot access hardware directly
- Kernel mediates all hardware access
- Interaction happens through defined interfaces

State this rule clearly and deliberately:

> User‑space programs **CANNOT touch hardware**  
> Not GPIO  
> Not registers  
> Not interrupts  

All hardware access is:
- Controlled
- Validated
- Mediated by the kernel

This rule explains:
- Why drivers exist
- Why system calls exist
- Why Embedded Linux systems remain stable

---

## TOPIC‑2: Why Interaction Is Needed at All

- Applications implement product logic
- Hardware control is required
- Safe mediation is mandatory

Embedded products exist to **do something physical**.

Typical requirements:
- Turn an LED on/off
- Read a sensor
- Communicate over UART, SPI, I2C

But applications:
- Run without hardware privileges
- Cannot access registers directly

Therefore:

> The kernel provides **defined doors**  
> Applications must use **only those doors**

---

## TOPIC‑3: The Big Picture Interaction Flow

    User Application
    → System Call
    → Kernel
    → Driver
    → Hardware

This is the **only valid execution chain**:

1. Application requests an operation
2. Kernel validates the request
3. Kernel invokes the correct driver
4. Driver accesses hardware
5. Result flows back to application

Critical insight:

> No user‑space request ever bypasses the kernel

This exact flow will be **implemented in Module‑9**.

---

## TOPIC‑4: System Calls – The Legal Gateway

- Controlled entry into kernel
- Initiated by user programs
- Enforced by CPU privilege levels

System calls exist because:
- CPUs support privilege separation
- User space runs unprivileged
- Kernel runs privileged

When an application calls:

```c
open(), read(), write(), ioctl()
````

What really happens:

1.  CPU switches to kernel mode
2.  Kernel executes the requested service
3.  Control returns safely to user space

This transition is **hardware‑enforced**, not optional.

---

## TOPIC‑5: POSIX APIs vs System Calls

    POSIX API ≠ System Call
    POSIX API → may trigger system call

Destroy a common misconception:

- `printf()` → no direct system call
- `open()` → system call
- `pthread_create()` → multiple system calls internally

POSIX APIs:

- Defined by standards
- Implemented by libraries (glibc)

System calls:

- Defined by the kernel
- Executed in kernel space


---

## TOPIC‑6: Major User ↔ Kernel Interfaces


- System calls
- /dev  – device files
- /sys  – sysfs
- /proc – kernel information

Linux exposes **four major interfaces** to user space:

- **System calls**  Direct service requests

- **/dev**  File‑based hardware access

- **/sys**  Attribute‑based control and configuration

- **/proc**  Kernel visibility and diagnostics

Embedded engineers must know **when to use which**.

---

## TOPIC‑7: `/dev` – Device File Interface

- File‑based interface
- Backed by device drivers
- open / read / write / ioctl

`/dev` provides a **file abstraction for hardware**.

Examples:

    /dev/ttyS0
    /dev/i2c-1
    /dev/gpiochip0

From user space:

- Devices look like files
- Kernel routes operations to driver callbacks

This is the **foundation of character device drivers**.

---

## TOPIC‑8: `/sys` – sysfs Interface


- Attribute‑based interface
- Exposes kernel objects
- Used to control hardware behavior

`/sys` is:

- Generated by the kernel at runtime
- A structured view of:
    - Devices
    - Drivers
    - Parameters

On BeagleBone Black:

- LEDs
- GPIOs
- PWM
    
are often controlled via `/sys`

Important rule:

> `/sys` is for **control and configuration**,  
> not bulk data transfer

---

## TOPIC‑9: `/proc` – Kernel Insight Interface

- Runtime kernel information
- Process and system status
- Debugging and diagnostics

`/proc` exposes:

- Process information
- Memory usage
- Kernel statistics

Examples:

- `/proc/cpuinfo`
- `/proc/meminfo`
- `/proc/interrupts`

Embedded relevance:

- Lightweight diagnostics
- Remote and field debugging

---

## TOPIC‑10: `/dev` vs `/sys` — Clear Distinction


/dev:
- Data path
- Device access
- Driver‑centric

/sys:
- Control path
- Configuration
- Attribute‑centric

Design guidance:

- Use `/dev` for:
    - Read/write data streams

- Use `/sys` for:
    - Enable/disable
    - Set parameters
    - Board configuration

Misuse leads to:

- Poor design
- Performance problems
- Maintenance pain

---

## TOPIC‑11: Blocking vs Non‑Blocking Interaction

- Blocking calls wait
- Non‑blocking calls return immediately
- Critical for embedded behavior

High‑level understanding:

- Blocking I/O:
    - Simpler
    - Can stall application logic

- Non‑blocking I/O:
    - More complex
    - Better responsiveness

Embedded implication:

> Poor blocking design  
> can freeze the entire product logic

This concept resurfaces in driver design.

---

## TOPIC‑12: `ioctl` — Controlled Custom Interface

- Custom control interface
- Beyond read/write
- Driver‑specific commands

Sometimes `read()` and `write()` are insufficient.

`ioctl` enables:

- Structured commands
- Driver‑specific control

Typical use:

- Mode selection
- Parameter configuration
- Status queries

Important caution:

> `ioctl` is powerful  
> and must be used sparingly and carefully

---

## TOPIC‑13: Security and Stability Rationale

- Kernel validates requests
- Prevents illegal access
- Preserves system stability

Reinforce the “why”:

- User code is untrusted
- Kernel code is trusted
- Interfaces must be narrow and validated

Embedded reality:

- No human interaction
- No recovery UI
- Stability > flexibility

Therefore:

> Strict kernel mediation is non‑negotiable

---

## Key Takeaways

- User space cannot touch hardware
- Kernel mediates all interaction
- System calls are the gateway
- /dev, /sys, /proc expose kernel
- Drivers enable safe hardware access
